# S5 candidate communication and activity history

14 October 2026. Engineering increment within the unchanged 98-requirement goal. S5 and release acceptance remain in progress.

## Reference and behavior

Reference `src/Candidates.gs` at checkout `7824be2`: `actAdd_`, `actVoid_`, `appGet_`, `ACT_TYPES_` and `CALL_OUTCOMES_`. The portal now adds **Communication and notes / سجل التواصل والملاحظات** inside candidate details.

- Recruiters with current native application read/write and recruitment management access can record a call, WhatsApp interaction, email interaction, meeting or note. Calls require a recognized outcome; meetings and notes require meaningful text. Notes are bounded to 2,000 characters. Recording an interaction does not send any communication or change the application stage, owner, next action or capacity.
- Every entry stores its original application/person association, actor, Cairo timestamp and content hash. There is no edit/delete command. Ordinary native DocType reads/writes are denied; the permission-checked portal/API is the supported route.
- The author or the company's configured HR approver, with current application permissions, can void a manual entry with a reason. A separate immutable `VOID` event links to the unchanged original. A unique link and serialized transaction prevent duplicate voids. Reserved `SYSTEM`/`STAGE` events cannot be manually created or voided through these commands. Administrator remains a privileged server operator.
- A person's history includes activities from their applications that the viewer can currently read. Permission filtering occurs before total counts and pagination. Other-application entries are read-only here and can open their source application. Raw actor identifiers are replaced with permission-filtered labels.
- The exact reviewed action uses the existing private encrypted recovery envelope. Lost replies freeze the original form; a retry or the Unfinished actions inbox recovers the same result. Completed-command replay rechecks current access. General hiring-request audits receive only references and hashes, not activity notes or void reasons.
- Independent append commands can both record distinct discussions against the same application version. Changing the application itself invalidates a stale reviewed version. Exact command replay returns one original event. Competing void commands allow only one cancellation.

## Storage and upgrade

The new exported DocType is `Kandil Candidate Activity`; the recovery operation enum adds `activity` and `activity_void`. Deploy the schema before serving the new frontend bundle, using the normal reviewed site migration process. The local parity and dedicated review sites used targeted `reload-doc` operations for these two DocTypes and web-only restarts; no production migration was performed.

The internal note uses Frappe's plain-text `Code` field with `Text` options. This preserves literal content instead of silently rewriting HTML-like text. The React portal and recovery review render text nodes, never HTML. The activity DocType has no ordinary native access. An explicit regression compares the hash against the saved fields for both notes and void reasons. No global sanitizer is disabled and no upstream core is changed.
