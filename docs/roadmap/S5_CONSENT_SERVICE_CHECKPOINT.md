# S5 candidate consent service — internal implementation

Date: 2026-10-14. The full 98-requirement goal remains active. **CAN-004 and the candidate consent journey remain partial.** This checkpoint implements the transactional service and immutable schema. No consent API is whitelisted, no candidate page is published and no recruiter link button is connected yet.

## Implemented behavior

- An authorized recruiter can internally issue a seven-day APPLY invitation against a specifically reviewed, currently published company notice. The application, person, employer, purpose, exact notice revision/hash, issuing actor, reason and expiry are recorded separately from consent.
- The service requires current account/role/grant/team and native document permissions before both new issuance and replay. Company/request serialization protects the replacement and acceptance decisions. The original issuer alone may retrieve the capability while still authorized and while that invitation remains pending.
- Invitations are append-only. Issuing a replacement requires the expected current invitation; replacement invalidates the previous link across that person's applications in the same company/purpose. Exact command retry returns the original non-secret receipt; changed payload or stale replacement fails.
- The 256-bit capability is a domain-separated HMAC using the site's encryption key and the opaque random invitation identity. Only its SHA-256 digest is persisted. The raw capability is absent from invitation records and command receipts. Rotating the site key prevents re-revealing a pending old link; a replacement is required. A previously distributed old capability remains usable until its ordinary expiry/replacement because lookup uses its stored digest. Rotation alone is therefore **not emergency link revocation**; an explicit revocation operation remains needed for operational rollout.
- The internal candidate preview returns only first name, job title, exact bilingual published notice, notice identifier/hash and expiry. It excludes contact details, candidate/application IDs, private history, compensation and documents. Display text remains plain text; a future browser must escape it.
- A Guest bearer response must explicitly accept the exact invitation's notice. Separate transfer acceptance is required only when that notice explicitly requests it. Staff sessions cannot use this candidate acceptance function.
- Acceptance appends a distinct immutable record with exact notice/hash, person/application/employer/purpose, timestamp and transfer response. Its evidence label is **Bearer link**. Link possession does not independently prove identity; a recruiter could possess a link in another browser. Do not describe this as identity-verified consent or legal certification.
- Unique invitation and company/person/purpose acceptance keys, Company locking and exact payload hashes support single-use consumption and exact retry. Repeating an accepted response returns only `accepted`, without a second record, including after expiry or a new notice revision. A changed retry fails. Independent-connection concurrency remains to be proved by the HTTP workflow harness.
- Changed/unpublished notice wording invalidates pending links. Historical acceptance is preserved unchanged when notices change; this matches the reference's distinction between recorded candidate-owned acceptance and recruiter/import notes. Withdrawal, reconsent, purpose/retention policy and eligibility consumers remain explicit unfinished work.
- The service never commits, contacts candidates, modifies candidate status, changes headcount, writes a follow-up or triggers external delivery. Controller guards deny native creation/copy/update/delete/rename outside the internal effect.
