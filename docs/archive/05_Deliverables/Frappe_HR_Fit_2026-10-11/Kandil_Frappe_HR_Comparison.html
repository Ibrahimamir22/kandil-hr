Frappe HR and the Kandil recruitment portal

Use Frappe HR as the HR foundation, with a separate Kandil custom app for the detailed recruitment and employee-lifecycle rules. It is not a drop-in replacement for everything in the portal.

الخلاصة: نستخدم Frappe HR كأساس لإدارة الموارد البشرية، ونطوّر فوقه إجراءات قنديل الخاصة. نظام الشركة الرئيسي وOdoo يظلّان مستقلّين، ويتم الربط بينهما بصلاحيات وواجهات API واضحة.

What this review establishes

The major differences that decide the architecture

  1. Position is not Designation. “Accountant” is a title; “Accountant seat 17 in factory A” is a structural position. The portal models that distinction. Add it explicitly rather than overloading a standard title.
  2. Headcount is not an offer count. Kandil reserves pending requests and fills capacity only when people join. The reviewed standard offer code checks submitted offers against a staffing plan. Reconciliation, concurrency and reversals need a dedicated design.
  3. One person can have several applications. Frappe supports multiple applications, but uses separate email-named Job Applicant records. The portal has a reusable Person master. Email-less workers must work through intake, interviews, offers and employee creation; fake emails are not a sound identity solution.
  4. Approvals are more than workflow arrows. Kandil resolves a position hierarchy, delegation, exceptions, board approval and what each approver saw. Generic workflow covers only part of that.
  5. Salary negotiation is not monthly payroll. The portal has gross/net offer calculations and authority rules but explicitly excludes payroll actions. Frappe adds a payroll engine; Egyptian payroll and tax/insurance calculations still need separate validation.
  6. BioTime enrollment is not attendance synchronization. Portal staff record enrollment and that access was stopped. Frappe has Employee Checkin and attendance processing, but connecting Kandil's BioTime deployment remains integration work.
  7. Probation and transfers are bespoke. The exact 30/60/75/80-day process, confidential surveys, insurance cases and temporary cover with automatic return are not standard equivalents.
  8. Audit history is not a cryptographic seal. Frappe tracks changes. The repo adds an HMAC chain. That is tamper-evidence under its key-control assumptions, not tamper-proof storage.

Implementation plan and acceptance gates

  1. Agree the HR record map. Employee, Person, Application, Position, Request Line, Vacancy, Reservation and Approval Snapshot need explicit ownership. Preserve source IDs for migration. Decide which portal rules remain necessary.
  2. Build a bounded proof before migrating. Demonstrate an email-less candidate all the way to Employee; a two-location request; two concurrent requests for the same last seat; a headcount exception with delegation and no self-approval; and an accepted offer followed by a real join or no-show.
  3. Configure standard HR. Set company/department/grade/roles, leave, onboarding templates, print formats and operational permissions. Use existing Desk screens for administrators initially.
  4. Build Kandil's custom app. Port approved rules and acceptance scenarios, not Apps Script storage/auth wrappers. Adapt the candidate UI to APIs. Add the position/reservation/request models and exact lifecycle rules.
  5. Connect external systems. Confirm the actual BioTime export/API. Define Odoo ownership and allowed updates. Establish shared login and role mapping for the company platform. Keep reliable retries and reconciliation logs.
  6. Rehearse and pilot. Import a representative sample, reconcile totals and documents, run role tests and recovery, and load-test realistic concurrent use. Employee count alone is not a capacity test. Roll out by agreed HR process or site after sign-off.

Decision gate: if the Person/Application and Position/headcount models require extensive changes to upstream internals, keep recruitment as a bounded custom component and pass hired employees into Frappe HR. That alternative still gives Kandil one company portal. It avoids committing the whole HR design before the hardest flows are proven.

Code reuse and migration

Reuse the blueprint, Arabic terminology, templates, question banks, score definitions and business-rule test cases. Existing HTML can inform or supply portions of the new UI, but its Apps Script API calls must change. The .gs services use Google storage, identity, triggers and locking; they do not run unchanged as Frappe server code. Preserve original request IDs, dates, consent versions, document provenance and historical approval evidence.

Later-release privacy, document, JD-review and security behavior may extend beyond the 98 headline requirements. Keep the release notes and source service inventory as migration inputs. This review maps every listed requirement; it does not claim exhaustive security review of every code path.

All 98 requirements

Configuration means a standard building block can be configured for the requirement, subject to testing. Custom means additional models, business logic or UI are needed for the exact behavior. Integration requires an external identity, AI or other service. Many Custom rows reuse standard functionality; these counts must not be read as a percentage of the whole HR system that must be rebuilt.

“No equivalent identified” is limited to the reviewed standard repositories. Third-party marketplace extensions were not assessed. Source links point to fixed commits for reproducibility.
